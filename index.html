How I work

Evidence over optimism

Test that it runs

Green tests are not enough

Tests can pass while the application fails to start. I add smoke checks that verify the app actually boots, catching real issues that unit tests miss.

Verify against reality

Mocks prove intent, not correctness

When integrating with external APIs, I write contract tests that run against the real endpoints. Mocks alone can hide surprising behavior.

Test-driven

No fix without a failing test

TDD, red then green: every change starts with a test that fails for the right reason, then the smallest fix that makes it pass.

Secure by construction

Make the wrong thing impossible

Security guarantees belong in code, not in documentation. I prefer designs where unsafe operations are structurally impossible rather than merely discouraged.

About

Background

I taught myself to program in 2018 (Python, JavaScript, Flask, Git, and Linux) and still learn that way. I formalised it with a full-stack program in React and Django. I build web applications and backend services for clients, and I also manage facilities.

I work test-driven and own the full software development lifecycle, from design to deployment. I develop with AI coding agents every day, under strict gates: a failing test before each fix and CI that proves the app actually boots. The speed comes from the agents. The correctness comes from the gates.

Away from the keyboard, I've spent ten years as a self-taught mechanic. Isolating a fault in a car and isolating one in software take the same habit: reproduce it, test one hypothesis at a time, and verify the fix. Since 2023 I've also installed 8 hyperbaric oxygen chambers as an independent contractor, and I still maintain 3 of them on a regular schedule.
